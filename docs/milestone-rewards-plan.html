Rewards Before the Card Is Full

Al Bab Al Abyad's paper card gives 50% off at visit 5 and a free wash at visit 9. The platform can only express the second one. This is what it takes to support the first — and why the order of work matters more than the work itself.

Al Bab Al Abyad Auto Services, Sharjah — nine slots, two rewards.

The reward at slot 5 is not a smaller prize. It is a retention device placed exactly where customers drift: past the novelty, not yet close enough to the finish to pull them back. The business spends a discount at the halfway point to buy the second half of the card.

Two properties matter for the build. Slot 5 does not complete the card — the customer collects the discount and keeps going. Slot 9 does — reward claimed, card starts again.

Why this isn't a small change

Redemption currently resets the card

In src/app/scan/actions.ts, claiming a reward writes a RewardRedemption row and then sets earnedStamps: 0, recalculating bonus stamps for a CARD_RESET event. Redemption and completion are the same act.

A visit-5 reward breaks that assumption: it must be claimable without resetting anything. This is the heart of the work — not the new table.

The rest of the model carries the same assumption. getRewardState() in src/lib/rewards.ts returns ACTIVE, REWARD_READY or REDEEMED from a single comparison against requiredStamps. There is no concept of which reward is ready, because there has only ever been one.

And a claimed milestone has to be remembered per card cycle. A customer who takes the 50% at visit 5, completes the card, and starts again should get the 50% again on the new card — but not twice on the same one.

Schema

One new table, plus one field to track what has been claimed in the current cycle.

// A reward at a point on the card. Every program gets at least one.
model ProgramReward {
  id                Int      @id @default(autoincrement())
  loyaltyProgramId  Int      @map("loyalty_program_id")
  atStamp           Int      @map("at_stamp")           // 5, 9
  rewardName        String   @map("reward_name")
  rewardDescription String   @map("reward_description")
  completesCard     Boolean  @default(false) @map("completes_card")

  loyaltyProgram    LoyaltyProgram @relation(...)
  redemptions       RewardRedemption[]

  @@unique([loyaltyProgramId, atStamp])
  @@index([loyaltyProgramId])
  @@map("program_rewards")
}

// On CustomerProgramMembership - cleared when the card resets.
claimedRewardStamps Int[] @default([]) @map("claimed_reward_stamps")

// On RewardRedemption - which milestone this was.
programRewardId Int? @map("program_reward_id")

completesCard is the field that carries the whole behavioural difference. Exactly one reward per program should have it set.

Why an array rather than a join table

claimedRewardStamps is bounded by the number of milestones on a card — a handful at most — and it is cleared on every reset. A join table would need the same clearing logic plus a cycle identifier to distinguish this card from the last one. The array keeps "claimed on the current card" in one place that resets naturally.

The four places code changes

  1. src/lib/rewards.ts Reward state becomes "which reward is ready", not "is the reward ready"

    getRewardState() and isRewardReady() take the program's reward list and the claimed set, and return the next unclaimed milestone the customer has reached — or none. Every caller of these two functions needs revisiting; they are the shared vocabulary the rest of the app uses.

  2. src/app/scan/actions.ts Redemption resets only when the claimed reward completes the card

    Record programRewardId on the redemption. Append atStamp to claimedRewardStamps. Reset earnedStamps and clear the claimed set only when completesCard is true. The existing idempotency key and transaction locking stay exactly as they are.

  3. card rendering + src/lib/google-wallet/mapper.ts The card shows where the rewards sit

    A customer who cannot see the visit-5 reward coming gets none of the retention benefit — the paper card works precisely because the badge is visible from day one. The Wallet pass needs the same: mapper.ts currently writes "N visits until {rewardName}", which must become the next reward rather than the final one.

  4. src/lib/programs.ts + program create/edit forms Business owners can add milestones

    A repeatable "at visit N, give X" row in program setup. programSchema validates: every atStamp between 1 and requiredStamps, no duplicates, exactly one completesCard, and that one at requiredStamps. This is the only part that is purely additive UI.

Do it in two stages

The stages are split by one property: whether the work gets harder once customers exist.

StageWhatWhen
Stage 1 Schema, backfill, reward-state logic, redemption behaviour, card and Wallet rendering Before the first customer enrolls
Stage 2 Milestone editor in program setup Any time after

Stage 1 changes nothing anyone can see. Every existing program gets exactly one ProgramReward row — at requiredStamps, with completesCard: true — which reproduces today's behaviour exactly. Same cards, same passes, same redemptions. It is a refactor with a migration, shipped while nobody is mid-card.

Stage 2 is then pure addition. A form and a badge. No migration, no customers to reason about, ship whenever.

The reason for the split

Every problem with adding this later is a people problem, not a code problem: a customer sitting at 6 stamps when a visit-5 reward appears, Wallet passes on real phones that now say the wrong thing, and redemption history with no milestone to point at. Stage 1 done early means those questions never arise. Schema and engine get harder with every customer; UI stays cheap forever.

Backfill

Additive and mechanical, in the shape of migration 0046:

  • Create program_rewards; add claimed_reward_stamps defaulting to []; add nullable program_reward_id to reward_redemptions.
  • For every existing LoyaltyProgram, insert one row: atStamp = requiredStamps, name and description copied from the program, completesCard = true.
  • Point existing reward_redemptions at their program's new row. Every past redemption was a card completion, because that is the only kind that existed.
  • Leave requiredStamps, rewardName and rewardDescription on LoyaltyProgram in place for now. Removing them is a second, separate migration once nothing reads them.

Run it the way 0046 went: prisma migrate deploy from a Windows terminal against PRODUCTION_DATABASE_URL, after testing on the dev branch. Vercel does not run migrations.

Decisions to make before writing code

  • Can a milestone be skipped? A customer reaches visit 9 without ever claiming the visit-5 discount. Do they lose it, or can they still claim it? Simplest rule: unclaimed milestones stay claimable until the card resets.
  • Can two rewards be ready at once? Follows from the above. If yes, staff need to pick which they are redeeming — that is a scanner UI change, not just logic.
  • Do bonus stamps count toward milestones? progressValue() combines earned and bonus. A customer starting with 2 bonus stamps is at visit 5 after 3 real visits. Probably fine, but it should be a decision rather than an accident.
  • What does the welcome WhatsApp message say? The approved new_loyalty_card template is fixed text with no reward mention, so nothing breaks — but a card with a reward at visit 5 is a better thing to advertise, and template changes need Meta approval.

What to test

  • A card with one milestone behaves exactly as it does today — this is the regression that matters most, since every existing program is that case.
  • Claiming at visit 5 does not reset stamps; the customer continues from 5.
  • The visit-5 reward cannot be claimed twice on one card.
  • After completing at visit 9, the card resets and the visit-5 reward is available again.
  • Redeeming the same milestone concurrently from two devices consumes it once — the existing idempotencyKey and row lock should cover this, but it needs proving with two milestones in play.
  • The Wallet pass names the next reward, not the final one, and re-syncs when the milestone is claimed.
